## ——クラウドに頼らず「対話で体調をモニタリングするアプリ」を個人開発した技術メモ

### はじめに：なぜ作ったのか

毎日の体調や心の状態を記録する、いわゆる「ジャーナリング」が続かない。理由はシンプルで、フォーマットに沿って自分で書くのが面倒だからだ。気分が落ちている日ほど、空欄を埋める気力が湧かない。

そこで発想を変えた。「自分で書く」のをやめて、「話す」ことにした。AIカウンセラーと数分だけ雑談する。すると裏でAIが内容を解析し、メンタルスコアやその日の感情、思考のクセを構造化データとして自動的に日記に書き残してくれる——そういうアプリを作った。

ポイントは、これを**一切クラウドに頼らず、自分のMacの中だけで完結させた**ことだ。心の状態という極めてプライベートな情報を、外部のAPIに送りたくなかった。OpenAIにもAnthropicにも送らない。録音した音声も、文字起こしも、AIの推論も、すべて手元のApple Siliconの上で動いている。

この記事では、そのために工夫した技術的なポイントを中心に紹介したい。「ローカルLLMで実用的なアプリを組む」ことに興味がある人の参考になればうれしい。

---

### 全体像：3つのAIが連携する

アプリの構成はシンプルなWebアプリだ。バックエンドはPythonのFastAPI、フロントエンドは1枚のHTML。ブラウザでマイクに向かって話すと、文字起こし→AIとの対話→要約・記録、という流れが回る。

技術スタックを並べるとこうなる。

- **推論エンジン**: Apple純正の機械学習フレームワーク MLX（Apple Silicon向けに最適化されている）
- **対話モデル**: Google の Gemma 4（4bit量子化してローカル実行）
- **音声認識（STT）**: Whisper large-v3-turbo を MLX 上で実行
- **音声合成（TTS）**: macOS 標準の `say` コマンド（Kyokoなどの日本語音声）にフォールバック
- **データ保存先**: Obsidian の Vault（Markdownファイル）

特に設計上おもしろいのが、**役割の違う「3つのAI」を1つのモデルで使い分けている**点だ。

1つ目は「カウンセラーAI」。ユーザーと実際に対話する役。20代前半の、データサイエンティストの分析力と心理カウンセラーの共感力をあわせ持つ存在、というキャラクター設定を与えている。タメ口で親しく話しかけてくる。

2つ目は「書記AI」。対話が終わると裏方に回り、会話の全体を読んで「メンタルスコア」「エネルギースコア」「今日の感情」「感謝したこと」「心理パターンの分析」を構造化されたJSONとして抽出する。

3つ目は「要約AI」。書記がまとめた日記をさらに100字に要約し、ポジティブ/ニュートラル/ネガティブの感情ラベルを付ける。これが翌日以降、「直近の傾向」として再びカウンセラーAIに渡される。つまり、AIが昨日までの自分を覚えている状態を作っている。

役割は違うが、動いているモデルの実体は同じGemma 4だ。プロンプトと出力フォーマットの指定だけで人格と仕事を切り替えている。複数モデルを並べるとメモリを食うので、1つを使い回すのは省メモリ上の必然でもあった。

### 工夫その1：投機的デコーディングで「待たされない」会話に

ローカルLLMの最大の弱点は速度だ。会話アプリで返事が10秒も20秒も返ってこないと、それだけで使う気が失せる。

ここで効いたのが**投機的デコーディング（Speculative Decoding）**、それもMLXのMTP（Multi-Token Prediction）方式だ。

仕組みをざっくり説明すると、小さくて速い「下書きモデル（draft model）」に先回りして数トークン分の続きを予測させ、大きくて賢い「本命モデル（main model）」がそれをまとめて検証する。予測が当たっていればその分まとめて確定できるので、本命モデルを1トークンずつ動かすより速くなる。品質は本命モデルのまま、速度だけ稼げるのがポイントだ。

実装上は、本命の `gemma-main` とは別に下書き用の `gemma-draft` を用意し、生成時に `draft_block_size=6`（一度に6トークン先まで投機）で渡している。

```python
response = generate(
    self.model, self.processor, prompt=prompt,
    draft_model=self.draft_model, draft_kind="mtp", draft_block_size=6,
    max_tokens=max_tokens, temperature=temperature, verbose=False
)
```

「会話の心地よさ」は体感速度に直結する。ここをサボらなかったことで、ローカルでも「待たされている感」がかなり薄れた。

### 工夫その2：メモリとの戦い——統合メモリを溶かさないために

Apple Silicon は CPU と GPU がメモリを共有する「ユニファイドメモリ」だ。これは強みでもあるが、LLM・音声認識・音声合成を同じマシンで順番に動かすアプリにとっては、メモリの奪い合いが起きやすい弱点にもなる。

対策を2段構えで入れた。

**1つ目は、全MLX処理を1本のスレッドで直列実行すること。** MLXのGPUストリームはスレッドローカルなため、対話モジュールと音声モジュールがバラバラのスレッドで動くとストリームが失われてクラッシュする。そこで `max_workers=1` のスレッドプールを1つだけ作り、すべてのMLX操作をそこに集約した。同時実行を禁じることで、メモリが一気に膨らむのも防いでいる。

```python
# MLXのGPUストリームはスレッドローカルのため、全モジュールで共有し、
# 全MLX操作を常に同一スレッドで直列実行する。
mlx_executor = ThreadPoolExecutor(max_workers=1, thread_name_prefix="mlx_worker")
```

**2つ目は、推論のたびにMetalのキャッシュを明示的に解放すること。** Gemmaの推論が終わった直後に `mx.metal.clear_cache()` を呼び、次に来るWhisperの文字起こしのためにメモリを空ける。逆もまた然り。この「お行儀のよい後片付け」を挟まないと、対話→音声の切り替えでメモリが詰まって落ちることがあった。

地味だが、ローカルで複数のAIを同居させるなら避けて通れない部分だ。

### 工夫その3：「対話」と「採点」を1回の推論で同時にやる

体調モニタリングである以上、ただ雑談して終わりではない。「睡眠」「今日の意図」「身体感覚」といった確認すべき項目を、会話の中で自然に拾っていく必要がある。

素朴に作るなら、「返事を生成するAI」と「項目を確認できたか判定するAI（Observer）」を分けて2回推論することになる。だがそれでは遅いし、メモリも倍食う。

そこで、**返答の生成と進捗判定を1回の推論に統合**した。カウンセラーAIには、ユーザーへの返事を書いたあと、返答の末尾に内部データとして進捗状況を1行だけ出力させる。

```
PROGRESS: {"sleep": true, "intention": false, "focus": false}
```

この `PROGRESS:` 行はサーバー側で正規表現で抜き取り、進捗管理に使ったうえで、画面表示やTTSに渡す前にきれいに削除する。ユーザーには見えない。推論1回で「気の利いた返事」と「裏側の状態管理」を両立させる仕掛けだ。

全項目が埋まるか、規定ターン数に達すると、自動的にクロージングへ移行して書記AIにバトンタッチする。ローカルLLMは出力フォーマットが不安定なこともあるので、`True`/`False`/`None`（Python形式）で返ってきてもJSONに正規化する、JSONパースに失敗したらフォールバックの定型文を返す、といった「壊れても止まらない」処理を随所に入れている。

### 工夫その4：データの置き場所をObsidianにした

記録の保存先は、自前のデータベースではなく **Obsidian の Vault**（要するにMarkdownファイルの集まり）にした。

理由は、データを「アプリの檻」に閉じ込めたくなかったからだ。日付ごとに `2026/06/2026-W23/2026-06-07.md` のような階層でファイルを書き出し、中身はObsidianが解釈できる形式にしている。

```
am_mental:: [7]
am_energy:: [6]
am_intention:: "焦らず一つずつ"
tags:: #mindfulness #session/morning
counselor_insight_am:: "回避傾向が和らぎ、受容的な構えが見られる"
```

`am_mental:: [7]` のような「データフィールド」形式で書いておくと、Obsidianのプラグインでメンタルスコアの推移をグラフ化できる。会話するだけで、自分の心身のログが自動的にグラフになって溜まっていく。重要なキーワードは `[[受容]]` のようにWikiLink化しているので、後から「受容について話した日」を横断的にたどることもできる。

アプリはあくまで「入力と解析の窓口」で、データの主権はユーザー側に残す。この割り切りは気に入っている。

### 心理学的な土台について

技術の話が中心の記事だが、中身の設計にも触れておきたい。書記AIが書く「インサイト（心理パターンの分析）」は、ACT（アクセプタンス&コミットメント・セラピー）、CBT（認知行動療法）、ポリヴェーガル理論といった枠組みの観点から書くよう指示している。

朝のセッションでは「今日どうありたいか（Being）」と身体感覚への注意を、夜のセッションでは感情の振り返りと「感謝できる3つのこと」を扱う。朝に立てた意図を夜に振り返れるよう、朝のログを夜のセッションに渡す——という形で、1日の中でも文脈がつながるようにした。

もちろんこれは医療行為ではないし、本物のカウンセリングの代わりにもならない。あくまで「自分の状態に毎日ちょっと立ち止まって気づくための道具」だ。そこは誇張せずに使っている。

### 作ってみて感じたこと

ローカルLLMは「動かすだけ」ならもう難しくない。難しいのはその先、**実用に耐えるアプリとして仕立てる**ところだった。速度（投機的デコーディング）、メモリ（直列実行とキャッシュ解放）、安定性（壊れても止まらないパース）——派手さはないが、この泥臭い部分こそが「毎日使えるかどうか」を分けた。

そして何より、心の記録のような繊細なデータを、誰にも渡さず自分の手元だけで扱える安心感は大きい。クラウドAIの便利さと引き換えに諦めていたものを、Apple Siliconの進化が少し取り戻してくれた感覚がある。
