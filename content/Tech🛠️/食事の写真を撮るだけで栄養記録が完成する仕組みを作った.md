「食事を記録すると痩せる」とはよく言われる。でも、実際に続けた人がどれだけいるだろうか。

僕は何度も挫折した。アプリを開いて、食品を検索して、量を入力して……というあの一連の作業が、毎食ごとに発生する。三日も経てば面倒になり、一週間後にはアプリの存在すら忘れている。記録のハードルが、記録から得られるメリットを上回ってしまうのだ。

そこで考えた。**「記録する」という行為そのものを、限りなくゼロに近づけられないか?** と。

たどり着いた答えがこれだ。**食事の写真を撮る。それだけ。** あとは全部、コンピュータが勝手にやってくれる。

## 何ができるのか

仕組みはとてもシンプルだ。

1. ご飯を食べる前に、iPhoneで写真を撮る
2. その写真を「食事」という名前のアルバムに入れる(共有アルバムやお気に入りで自動振り分けもできる)
3. ……以上。あとは何もしない

すると、放っておいても、こんなことが裏側で起こっている。

- Macが定期的にアルバムをチェックして、新しい写真を見つける
- 写真をAIに送り、料理名・カロリー・PFC(タンパク質・脂質・炭水化物)を分析させる
- 分析結果を、その日のObsidianデイリーノートに自動で書き込む
- 処理が終わった写真には「記録済み」の印をつけて、二度と重複処理しない

気づけば、Obsidianの中に自分の食事ログが勝手に積み上がっている。「今日は何カロリー摂ったか」「今週のタンパク質は足りているか」が、写真を撮っただけで可視化される。

記録のために頭を使う場面が、文字通り一つもない。これが、僕が三日坊主を脱出できた理由だ。

## なぜObsidianなのか

栄養管理アプリは世の中に山ほどある。それでも自前でObsidianに記録する道を選んだのには理由がある。

データが自分の手元に、プレーンテキストで残るからだ。食事の記録は、突き詰めれば「自分という人間のログ」だ。それを特定のサービスに預けてしまうと、サービスが終了したり仕様変更したりした瞬間に、過去の自分が消える。Markdownのテキストファイルなら、10年後も自分のものとして読める。

そしてObsidianには[Dataview](https://github.com/blacksmithgu/obsidian-dataview)という強力なプラグインがある。ノートに構造化したデータを埋め込んでおけば、それを後から自由に集計・可視化できる。今回はこの仕組みをフル活用した。

## 仕組みの中身

ここからは、どう作ったかの技術的な話。全体はPythonのスクリプト1本と、macOSの標準機能の組み合わせでできている。新しいサーバーもクラウドも要らない。手元のMacだけで完結する。

処理の流れを図にするとこうなる。

```
[iPhoneで撮影]
      ↓ iCloud同期
[Mac の「食事」アルバム]
      ↓ AppleScript で書き出し
[一時フォルダの画像]
      ↓ Gemini API で分析
[料理名・カロリー・PFC の JSON]
      ↓ Markdown に整形
[Obsidian デイリーノート]
      ↓ 処理済みマーク
[「記録済み」キーワード付与]
```

### 1. 写真をどう取り出すか — AppleScript

最初の関門は、「写真」アプリのアルバムからどうやってプログラムで画像を取り出すか、だった。

macOSの「写真」アプリは、画像を独自のライブラリ内に隠している。普通のフォルダのように `ls` でアクセスできない。ここで使ったのがAppleScriptだ。macOSのアプリを外部から操作できる、古くからある自動化言語で、「写真」アプリも対応している。

Pythonから `osascript` コマンド経由でAppleScriptを呼び出し、「食事」という名前のアルバムを探して、中の写真を一時フォルダに書き出す。書き出した写真のIDとファイル名はJSONで受け取る。

```python
result = subprocess.run(
    ["osascript", "-e", script],
    capture_output=True, text=True
)
```

ちなみにここで地味にハマったのが、AppleScriptのコードをPythonのf-stringで組み立てようとすると、AppleScript側の `{}` 記号とPythonの波括弧が衝突すること。結局 `str.replace()` で泥臭くプレースホルダを置換する方式に落ち着いた。

### 2. 写真から栄養を読み取る — Gemini

取り出した画像を、GoogleのGemini APIに投げる。ここがこの仕組みの心臓部だ。

ポイントは**プロンプトの設計**にある。AIに「この食事の写真を分析して」と漠然と頼むと、毎回バラバラな形式で長々と返ってくる。それでは後の処理で使えない。そこで、出力を厳密にJSONだけに固定するよう指示した。

```
You are a nutritionist. Analyze this meal photo and respond
with ONLY a JSON object. No explanation, no preamble, no markdown.
```

「説明も前置きもMarkdownもいらない、生のJSONだけ出せ」と念を押す。それでもAIは時々コードブロックで囲んで返してきたり、余計な一言を添えたりする。だから受け取った側でも、正規表現でJSON部分だけを確実に抜き出す保険をかけている。

```python
code_block = re.search(r"```(?:json)?\s*(\{.*?\})\s*```", text, re.DOTALL)
```

AIとやり取りする実用システムでは、「AIは指示通りに動かないことがある」という前提でガードを二重三重にかけておくのが効く、というのが今回の学びだった。

返ってくるのは、こんなデータだ。

```json
{
  "meal_name": "鮭の塩焼き定食",
  "calories": 650,
  "protein": 38.5,
  "fat": 22.0,
  "carbs": 70.0,
  "notes": "ご飯は中盛り程度"
}
```

### 3. Obsidianに書き込む — Dataview形式

分析結果を、その日のデイリーノートに追記する。ノートのパスは `年/月/年-週番号/日付.md` という構造で、ISO週番号(月曜始まり)を使ってObsidian側の設定と揃えている。ファイルがなければ自動で作る。

書き込むときは、Dataviewが後で集計できる「インラインフィールド」という形式を使う。

```
食事記録:: [食事名: "鮭の塩焼き定食", 時刻: "12:34",
カロリー: 650, タンパク質: 38.5, 脂質: 22.0, 炭水化物: 70.0, 備考: ""]
```

ちなみに撮影時刻は、AIには頼らない。写真のEXIF情報(`DateTimeOriginal`)から実際の撮影時刻を読み取っている。「いつ食べたか」は写真自身が一番正確に知っているからだ。

この形式でログを溜めておくと、Dataviewのクエリ一発で集計できる。例えば今週の合計カロリーとPFCはこう。

````
```dataview
TABLE
  sum(rows.r.カロリー) as "合計カロリー (kcal)",
  sum(rows.r.タンパク質) as "合計タンパク質 (g)"
FROM "01_journal"
FLATTEN 食事記録 as r
WHERE r AND file.mtime >= date(today) - dur(7 days)
GROUP BY true
```
````

さらに別途、その日の合計カロリーをノートのフロントマターに `Calorie:` として書き込む処理も入れた。これでノート一覧から「カロリーの多い日」をソートしたりできる。

### 4. 二度処理しない工夫

自動化で一番怖いのは、同じ写真を何度も処理して記録が重複することだ。これを二段構えで防いでいる。

ひとつは、処理済み写真のIDを `processed.json` に記録しておくこと。次回実行時はこのリストにあるIDを除外する。

もうひとつは、処理し終えた写真に「記録済み」というキーワード(タグ)を「写真」アプリ側で付けること。こうすれば、自分が「写真」アプリを開いたときにも、どれが処理済みか一目でわかる。

> 余談だが、当初は処理済み写真をアルバムから自動で削除する設計だった。ところがmacOSのアップデート(Tahoe)で「アルバムから写真を削除する」AppleScriptの構文が使えなくなり、急遽キーワード付与方式に切り替えた。OSの自動化機能に乗っかると、こういうOS側の都合に振り回されるのは宿命でもある。

### 5. 全自動で回す — launchd

最初はcronで組んだのだが、途中でmacOS標準の `launchd` に移した。理由はシンプルで、**ノートPCは実行予定の時刻に閉じて寝ていることが多い**からだ。cronはその時刻にMacがスリープしていると、その回をまるごと取りこぼす。一方launchdは、予定を逃しても次にMacが起きたタイミングで実行してくれる。個人のMacで動かす自動化とは、launchdの方が相性がいい。

役割の違う2つのエージェントを `~/Library/LaunchAgents/` に置いている。

**ひとつ目は写真を取り込む本体**。`StartInterval` を使って30分ごと(1800秒)に走らせる。固定時刻ではなく短い間隔で回しておくことで、いつ食事の写真を撮っても、長くても30分後には記録が完成する。

```xml
<key>StartInterval</key>
<integer>1800</integer>
```

**ふたつ目は1日の締めの集計**。`StartCalendarInterval` で毎日23:59に `main.py --summarize` を実行し、その日のカロリーを合計してノートのフロントマターに書き込む(セクション3で触れた処理だ)。「取り込み」と「集計」を別エージェントに分けることで、それぞれを独立した間隔で回せる。

```xml
<key>StartCalendarInterval</key>
<dict>
    <key>Hour</key><integer>23</integer>
    <key>Minute</key><integer>59</integer>
</dict>
```

あとは `launchctl load ~/Library/LaunchAgents/com.okamiyatakashi.food-nutrition-logger.plist` のように読み込めば、登録完了だ。

これで、人間が関与する場面は「写真を撮ってアルバムに入れる」だけになった。残りは全部、Macが30分おきに静かに片付けてくれる。

## 作ってみて思うこと

この仕組みの本質は、栄養管理そのものより「面倒な記録を、習慣の中に溶かし込む」ことにあると思っている。

写真を撮るのは、もともと多くの人がやっている行為だ。その「ついで」に記録が完成するなら、新しい習慣を増やす必要がない。続かないのは意志が弱いからではなく、仕組みが人間に無理をさせているからだ——というのが、何度も挫折した末の僕の結論だ。

AIの進歩で、「写真一枚から構造化データを取り出す」ことが個人レベルでも当たり前にできるようになった。同じ発想は、レシートから家計簿、本棚の写真から蔵書管理、ホワイトボードの写真から議事録……といろいろ応用が効くはずだ。「撮るだけで記録が終わる」世界は、思っているより近い。

身の回りの「面倒な記録」を、ひとつずつコンピュータに肩代わりさせていきたい。
